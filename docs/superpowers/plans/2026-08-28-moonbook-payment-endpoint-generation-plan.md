# Moonbook 支付地址自动生成与 GM Pay v2 同步实施计划

## 1. 约束

- 依据 `docs/superpowers/specs/2026-08-28-moonbook-payment-endpoint-generation-design.md` 实施。
- 两个基础地址是唯一地址配置事实，五个业务端点只能由后端派生。
- GM Pay v2 无签名查单结果不得直接触发财务入账。
- 已执行迁移只增不改，新迁移版本为 `00074`。
- Long ID 在管理 API 和前端始终按字符串处理。
- 不连接或修改生产支付、数据库和部署环境，不执行真实支付，不 `git push`。

## 2. 实施任务

### 任务一：数据库与后端地址模型

- [ ] 新增 `00074_payment_channel_base_urls.sql`，增加 EPUSDT 与读者端基础地址列，不回填、不启用现有渠道。
- [ ] 更新迁移 manifest 与迁移契约测试。
- [ ] 在 `adminpayment` 中增加基础地址字段、严格 origin 校验、规范化和确定性端点派生函数。
- [ ] 管理写接口只接收两个基础地址，查询响应返回基础地址和五个只读派生地址。
- [ ] Repository 只写基础地址；运行配置按读取到的基础地址派生创建、回调、跳转、健康和同步端点。
- [ ] 更新 CRUD、运行配置、启用完整性和 HTTP 契约测试。
- [ ] 提交：`实现支付渠道地址自动生成`。

### 任务二：GM Pay v2 安全状态同步

- [ ] 将同步请求改为对转义后的 `gateway_trade_id` 执行 GET。
- [ ] 严格解析 GM Pay envelope，限制响应体、校验 HTTP 状态、`trade_id` 和状态枚举。
- [ ] 实现等待支付、已支付但缺回调、已过期和等待选择网络四种状态映射。
- [ ] 保证同步状态更新与审计同事务、已支付幂等、无签名响应绝不写钱包流水。
- [ ] 更新管理端同步结果提示，明确状态不一致时需在 GM Pay 重发回调。
- [ ] 覆盖成功状态、异常响应、转义、事务和重复执行测试。
- [ ] 提交：`适配GM Pay订单状态同步`。

### 任务三：管理前端

- [ ] 将五个可编辑地址输入改为 EPUSDT 基础地址和读者端基础地址。
- [ ] 展示五个只读派生地址并提供复制图标，保持对话框单层结构和响应式布局。
- [ ] 新增与编辑载荷只提交两个基础地址；启停请求沿用列表中的基础地址。
- [ ] 更新 URL 校验、未配置编辑状态和前端契约测试。
- [ ] 提交：`简化支付渠道地址配置`。

### 任务四：综合验证与收尾

- [ ] 使用项目专用真实 PostgreSQL 验证从现有版本升级到 `00074`、迁移历史和关键业务数据不减少。
- [ ] 执行支付模块 Go 单元与集成测试、`go vet`。
- [ ] 执行管理前端定向测试、静态检查和生产构建。
- [ ] 执行秘密扫描、`git diff --check`，检查全部已跟踪和未跟踪修改。
- [ ] 按逻辑提交所有有效修改并确认工作区干净。

## 3. 完成标准

- 管理员只需填写两个基础地址即可得到确定的五个端点。
- API 调用者不能覆盖派生端点，运行配置不再读取旧五列。
- GM Pay v2 状态同步可识别四种状态，支付成功缺回调时不会直接入账。
- 签名回调仍是支付入账的唯一入口，支付幂等和钱包流水约束不回退。
- 数据库、后端和管理前端验证全部通过，无秘密进入仓库。

## 4. 服务影响

- `server`：需要重新构建并重启，启动时执行新增 PostgreSQL 迁移。
- `web`：需要重新构建并发布。
- PostgreSQL：新增两个非敏感基础地址列，不删除或回填业务数据。
- `reader-ui`、网关、Redis 和对象存储：无代码或配置变更，无需因本功能重启。
