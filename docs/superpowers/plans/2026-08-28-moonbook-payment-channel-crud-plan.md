# Moonbook 支付渠道安全 CRUD 实施计划

## 1. 约束

- 依据 `docs/superpowers/specs/2026-08-28-moonbook-payment-channel-crud-design.md` 实施。
- 不导入旧 EPUSDT 环境变量配置，不保留历史凭据。
- 全项目只使用 `MOONBOOK_APP_MASTER_KEY`，禁止模块专属主密钥。
- 不连接真实支付环境，不执行真实支付，不修改生产数据，不 `git push`。
- Long ID 在 API 和管理前端始终按字符串处理。
- 工作区现有购买与旧数据迁移修改来源不明，保持原样并与本功能提交隔离。

## 2. 实施任务

### 任务一：统一加密服务与迁移

- [ ] 新增 `internal/platform/secretcrypto`，实现 Base64 32 字节主密钥解析、AES-256-GCM、版本密文信封和 AAD 隔离。
- [ ] 覆盖随机 nonce、篡改、跨字段复制、非法密钥和秘密不进入错误文本。
- [ ] 新增最高版本 Goose 迁移，扩展 `reader_payment_channels`、改为 identity ID、增加活动 provider 条件唯一索引、约束和 CRUD 权限。
- [ ] 更新迁移清单测试，验证空库、升级和幂等重跑。
- [ ] 提交：`新增支付渠道加密存储基础`。

### 任务二：后端 CRUD 与动态运行配置

- [ ] 重构 `adminpayment` 的 DTO、Repository、Service 和 Handler，支持列表、详情、新建、编辑、启停、检查和归档。
- [ ] 新增数据库运行配置 Provider，解密并构造 EPUSDT 客户端配置。
- [ ] 创建订单时按请求读取配置快照，不使用启动期环境变量客户端。
- [ ] 回调验签、主动同步和连通性检查按操作读取当前配置。
- [ ] 过期窗口读取数据库配置并保留无配置时的安全默认值。
- [ ] 进行中订单下禁止替换凭据和归档，写入与保护检查在同一事务完成。
- [ ] 新增 CRUD、动态生效、回调、同步、检查和脱敏集成测试。
- [ ] 提交：`实现支付渠道动态配置接口`。

### 任务三：管理前端

- [ ] 扩展 `paymentChannels.js` CRUD API，所有 ID 使用 `appendLongId`。
- [ ] 重做支付渠道页面：工具栏、归档过滤、状态列、图标操作和检查结果。
- [ ] 新增单层新建/编辑对话框，按基本信息、凭据、端点和超时分组。
- [ ] 新建要求 PID/Secret，编辑留空保持原值，不回填秘密。
- [ ] 增加启停与归档确认、字段校验、错误状态和稳定布局。
- [ ] 补充页面/API 测试并执行 ESLint、生产构建。
- [ ] 提交：`新增支付渠道配置管理页面`。

### 任务四：审计、部署文档和综合验证

- [ ] 为支付渠道写接口使用敏感字段清洗后的操作记录，验证请求和响应均不泄漏秘密。
- [ ] `.env.example`、Compose 和 Server 容器注入 `MOONBOOK_APP_MASTER_KEY`，移除应用对 EPUSDT 专属环境变量的读取。
- [ ] 更新部署文档，说明唯一主密钥生成、注入、备份、丢失和禁止直接轮换规则。
- [ ] 更新重构进度和相关旧设计的替代说明，避免后续继续沿用旧配置方式。
- [ ] 使用真实 PostgreSQL 验证迁移与关键集成测试；执行 Commerce/Reader 定向 Go 测试、`go vet`、管理前端测试和生产构建。
- [ ] 检查秘密扫描、`git diff --check`、暂存区和全部工作区状态。
- [ ] 提交：`完善统一主密钥部署与支付配置验证`。

## 3. 完成检查

- [ ] 页面可完成 EPUSDT 渠道新建、脱敏查看、编辑、启停、检查和归档。
- [ ] 配置保存后下一次支付操作立即生效，无需重启。
- [ ] API、日志、操作记录、数据库非密文字段和前端状态不包含 PID/Secret 明文。
- [ ] 当前开发环境不依赖旧 EPUSDT 环境变量或历史凭据。
- [ ] 进行中订单保护、支付幂等和资金事务不回退。
- [ ] 项目只声明一个 `MOONBOOK_APP_MASTER_KEY`。
- [ ] 所有本功能有效修改已按逻辑使用简体中文提交，未擅自提交或覆盖来源不明修改。

## 4. 服务影响

- 后端 `server`：需要重新构建并重启；启动前必须注入 `MOONBOOK_APP_MASTER_KEY`。
- 管理前端 `web`：需要重新构建并发布。
- PostgreSQL：需要运行新增 Goose 迁移，不删除现有业务数据。
- Reader 前端：不修改代码，无需单独重建；支付行为由后端动态配置影响。
- Redis、对象存储：无配置或数据变更，无需重启。
