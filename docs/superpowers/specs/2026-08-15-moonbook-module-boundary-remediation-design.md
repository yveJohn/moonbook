# Moonbook 模块边界整改设计

## 1. 文档状态

- 日期：2026-08-15
- 状态：主体设计及 Commerce 定向 Reader 搜索投影已获用户批准，修订规格待用户复核
- 范围：修复 Reader、Commerce、Novel 之间的实现依赖和数据所有权违规
- 依据：总体批准设计、M7 后端质量基线与跨域工作流清单

本设计关闭 `TestModuleDependencyRules` 报告的 15 处跨模块实现引用，并消除已审计的跨域 SQL 访问。整改必须保持冻结 Reader HTTP 契约、Long ID 字符串规则和现有跨域事务语义，不通过跳过测试、复制业务规则或扩大共享数据库访问来换取边界测试通过。

## 2. 背景与问题

当前 CI 后端质量门确定失败：Commerce 的 Reader-facing HTTP 包直接依赖 Reader 鉴权和序列化实现；Reader 公开与账号接口直接依赖 Commerce、Novel 实现；至少 11 个实现文件还直接访问其他领域拥有的表。

违规归并为九类工作流：Reader 路由认证与输出、公开书库/章节/正文、账号商业视图、邀请注册奖励、个人内容投影、点赞汇总、Commerce 管理端读者校验、邀请首充奖励、商品目标与购买报价。完整现状和必须保持的不变量见：

- `docs/verification/m7-backend-quality-baseline.md`
- `docs/verification/m7-module-boundary-workflow-inventory.md`

## 3. 目标与非目标

### 3.1 目标

- Reader、Commerce、Novel 只通过目标领域公开的窄合同协作；
- Reader 拥有全部冻结 Reader HTTP 路由、DTO、认证和错误映射；
- `initialize` 是唯一跨领域实现装配位置；
- 任何领域不得直接读取或修改其他领域的表；
- 注册奖励、点赞、购买和首充奖励继续保持同一 PostgreSQL 事务内的原子性与幂等；
- 查询投影优先使用批量合同；Commerce 管理搜索使用 Commerce 自有的最小 Reader 搜索投影，消除跨域 JOIN 且不引入 N+1；
- 原样保持冻结 Reader 路径、方法、响应、空值、日期、鉴权和 Long ID 字符串合同；
- 原样保留边界测试并增加 SQL 所有权、并发、回滚和故障证据。

### 3.2 非目标

- 不拆分微服务，不引入消息中间件、分布式事务、CDC 或双写；
- 不修改冻结 Reader UI 业务代码；
- 不改变管理页面功能、Reader 产品行为或业务状态机；
- 不为领域内部每个子包建立合同，领域内部仍可直接协作；
- 除新增 Commerce 自有的最小 Reader 搜索投影及其索引外，不借本次整改扩展数据库结构；其他约束或索引仍须单独走迁移设计和验证门；
- 不借本次整改实施监控、安全依赖升级、M4 支付补全或 M5/M6 数据迁移功能。

## 4. 备选方案

### 4.1 方案 A：领域合同、Reader 兼容编排和上下文事务，采用

每个数据所有者发布窄合同，Reader 统一承载兼容 HTTP，`initialize` 注入实现。平台 Transactor 将事务绑定到派生 Context，跨域合同调用自动加入同一事务。

优点是所有权清晰、现有原子性可保持、单体部署不变、未来 k3s 或 Worker 拆分边界明确。代价是需要拆分当前 Handler/Repository，并为批量投影和事务参与者补充合同测试。

### 4.2 方案 B：把所有 Reader-facing 逻辑整体搬入 Reader，拒绝

该方案可以快速清除 Commerce HTTP 对 Reader 的 import，但会把商品、钱包、权益、支付和小说规则复制或转移到 Reader。它只是移动违规，破坏数据所有权并形成新的巨型兼容模块。

### 4.3 方案 C：建立共享查询库或通用跨域读模型，拒绝作为本次方案

共享查询库可以保留跨表 JOIN，通用读模型可以降低在线组合成本，但前者继续绕过所有权，后者需要事件平台、通用回填和额外一致性机制。当前容量和单体边界没有证明需要这项复杂度，且它不能解决注册、点赞、购买和首充奖励的原子事务。

本次采用的 `commerce_reader_search_projection` 不是共享库或通用跨域读模型。它是经单独批准的窄例外，只归 Commerce 所有，只保存 Commerce 管理端准确筛选、计数、分页和展示所需的四个 Reader 字段，并通过同库事务同步；其他领域不得复用它，Commerce 也不得用它作鉴权或交易判断。

## 5. 架构与所有权

Reader 拥有读者账号、认证会话、邀请码与邀请关系、书架、阅读历史、偏好、点赞关系、反馈，以及冻结 Reader HTTP 契约的路由、DTO、错误和日期映射。

Commerce 拥有钱包与不可变流水、商品、购买订单、充值订单、会员授予、权益、签到和邀请奖励配置，以及仅供自身管理搜索使用的 Reader 最小投影。`reader_wallets`、`reader_wallet_ledgers` 和 `reader_purchase_orders` 虽有历史前缀，仍属于 Commerce。

Novel 拥有分类、书籍、章节、发布可见性、SEO、正文对象引用与已校验正文读取。

Platform 提供 PostgreSQL 事务、配置和横切能力，不拥有业务事实。`initialize` 只负责构造、注入和注册，不承载业务规则。

## 6. 合同与组件

### 6.1 Reader 合同

`reader/contract` 按用例提供：

- 账号存在、状态和事务内锁定；
- 单个及批量读者显示信息；
- 有效邀请关系查询；
- 其他 Commerce 工作流确实需要的最小 Reader 事实。

### 6.2 Commerce 合同

`commerce/contract` 按用例提供：

- 当前权益与会员状态；
- 会员商品和内容商品批量投影；
- 钱包、流水、签到、购买和充值应用能力；
- 邀请奖励配置与事务内奖励参与者；
- Reader 兼容账号面板需要的商业汇总；
- Reader 账号写流程需要的搜索投影同步与一致性修复能力。

### 6.3 Novel 合同

`novel/contract` 按用例提供：

- 已发布书籍、章节、分类和 SEO 查询；
- 批量书籍/章节展示快照；
- 已校验章节正文读取与导航；
- 商品目标校验和购买快照；
- 事务内书籍锁定与点赞汇总更新。

### 6.4 合同约束

- 合同按用例拆成窄接口，不建立全领域巨型 Service；
- DTO 只表达领域数据，不包含 Gin Context、GVA Model、具体 Repository、表名或 HTTP 响应；
- 合同不得导出 `*sql.DB`、`*sql.Tx` 或其他实现句柄；
- Provider Adapter 在所属领域内实现合同，并使用编译期断言；
- Consumer 只依赖目标领域 `contract` 包，测试使用窄接口替身；
- 业务模块不能自行构造其他领域实现，也不能通过共享数据库连接绕过合同。

### 6.5 Reader 兼容层

当前位于 Commerce 包内的签到、购买、充值和钱包 Reader HTTP Handler 迁入 Reader 兼容层。Reader 统一负责：

- 冻结路由注册和认证中间件；
- 请求解析、日期格式和 Long ID 字符串转换；
- `code/message/data/rows/total` 等兼容包装；
- 合同错误到冻结 Reader 错误的映射。

Commerce 继续拥有并实现对应业务规则，Reader Handler 只做兼容编排。

### 6.6 Commerce Reader 搜索投影

新增 Commerce 自有表 `commerce_reader_search_projection`，字段固定为：

- `reader_id bigint`：主键，保持 Reader Long ID 原值；
- `username`：管理端订单、充值订单和钱包搜索字段；
- `nickname`：管理端钱包搜索和展示字段；
- `status`：管理端展示及已存在筛选所需的账号状态快照；
- `created_at`、`updated_at`：投影维护与漂移审计时间。

该表不对 `reader_accounts` 建立外键，避免以数据库约束形成反向领域耦合；唯一性、长度和状态约束必须与 Reader 源字段兼容，并为用户名、昵称和状态的既有查询方式建立可验证索引。投影不保存密码、联系方式、邀请关系、认证信息或其他 Reader 事实。

Reader 是这些字段的唯一事实来源。注册、管理端账号编辑、状态变更及以后任何会改变上述字段的账号写流程，必须在同一个 Platform `Transactor` 中先写 Reader 事实，再通过 Commerce 窄合同 upsert 投影；删除流程若未来存在，则在同一事务删除对应投影。投影同步失败必须使整个账号写事务回滚，不能提交陈旧投影，也不引入异步最终一致双写。

前向迁移新增版本 `00059`：创建表和索引后，从现有 `reader_accounts` 一次性幂等回填。迁移脚本是受控的结构升级边界，可以读取源表完成初始回填；运行时 Commerce 实现仍禁止读取 Reader 表。空库迁移、已有数据升级和重复执行必须验证，已经提交或执行的 `00001` 至 `00058` 不得修改。

旧 MySQL 账号迁移写入 `reader_accounts` 时，必须在同一目标 PostgreSQL 事务内通过 Commerce 合同维护投影，并保持检查点和幂等重跑语义。不得依赖“先迁账号、最后补投影”的无保护窗口作为正式迁移路径。

Reader 提供分页账号搜索快照，Commerce 提供分页投影快照和幂等修复合同。Reader 侧的一致性应用服务经合同对比缺失、多余和字段不一致记录，并输出数量与 Reader ID 脱敏清单；获授权的修复模式按 Reader 事实 upsert 或删除 Commerce 投影。该流程由 `initialize` 注入依赖，但业务规则不写入 `initialize`，双方实现都只能访问本领域表。

## 7. 事务协调

平台层提供 `Transactor.Within(ctx, fn)`：

1. 最外层调用开启 PostgreSQL 事务并创建派生 Context；
2. 领域 Repository 从 Context 取得当前事务，否则使用自身数据库连接；
3. 合同方法只传递 Context，Provider 自动加入当前事务；
4. 只有发起跨域用例的应用编排器调用 `Within`，Provider 合同参与已有事务，不自行开启独立事务；
5. 嵌套 `Within` 加入已有事务，不独立提交；任一嵌套回调返回错误会把作用域标记为 rollback-only，即使上层误吞错误，最外层也拒绝提交；
6. 只有最外层提交或回滚；panic 必须标记 rollback-only、回滚并继续传播；
7. `AfterCommit` 回调只在成功提交后执行，用于缓存失效等非事实操作。

事务绑定机制由 Platform 封装。业务合同和 DTO 不暴露 `*sql.Tx`。Repository 只能使用事务访问自己领域的表，新增 SQL 所有权测试持续约束这一点。

### 7.1 邀请注册

Reader 锁定邀请码，创建账号、自动邀请码和邀请关系，并同步 Commerce Reader 搜索投影。关系首次创建后，Commerce 在同一事务读取奖励配置并写入双方幂等钱包流水。账号、投影、关系、邀请码计数或任一奖励失败时全部回滚，不留下半注册、搜索缺口或单边奖励。

### 7.2 点赞

Novel 在事务内锁定有效书籍。Reader 幂等写入或删除点赞关系并计算精确关系总数，Novel 随后更新 `like_count`。关系和汇总同成同败，并发结束后汇总必须等于关系行数。

### 7.3 购买

Commerce 发起事务，通过 Reader 合同校验账号，通过 Novel 合同读取有效购买快照，然后在 Commerce 内完成报价、订单、钱包扣款、不可变流水、会员授予或内容权益。任一步失败全部回滚，现有业务幂等键继续生效。

### 7.4 首充奖励

Commerce 锁定充值或补单事实，通过 Reader 合同取得有效邀请关系，再完成钱包入账、首充奖励和订单终态。模拟充值、支付回调和人工补单继续共用现有幂等事实，跨入口只发放一次。

### 7.5 锁顺序

跨域流程统一按以下类别获取锁：

1. 业务幂等或聚合 advisory lock；
2. Reader 账号、邀请码或邀请关系；
3. Novel 书籍或章节目标；
4. Commerce 订单、权益或奖励事实；
5. Commerce 钱包。

具体工作流可以跳过不需要的类别，但不能逆序获取。并发测试必须覆盖死锁超时和重试入口。

## 8. 查询与投影数据流

跨域只读接口不再使用 SQL JOIN 读取其他领域表：

- Reader 先读取书架、历史、点赞等自身事实，批量收集书籍和章节 ID，再由 Novel 批量合同补齐名称、状态和展示字段；
- Commerce 订单和充值订单管理列表把自有业务事实与 `commerce_reader_search_projection` 关联，在 Commerce 内完成用户名筛选、准确总数、稳定排序和数据库分页；
- Commerce 钱包管理列表以 `commerce_reader_search_projection` 为驱动表左连接自有钱包事实，按用户名或昵称筛选，使尚未创建钱包的 Reader 账号仍出现在结果中；
- 其他只需少量 Reader 展示字段且不参与筛选或分页的 Commerce 管理查询，优先通过 Reader 批量合同补齐；确需使用投影时必须仍限于管理搜索和展示；
- Reader 公开书库先由 Novel 返回内容，再由 Commerce 批量叠加价格、权益和会员状态；
- Reader 账号商业视图直接调用 Commerce 合同，不查询 Commerce 表；
- Commerce 商品目标和购买报价调用 Novel 合同，不查询 Novel 表。

批量合同必须保持调用方要求的稳定排序、缺失关联、空值和分页语义。调用方按 ID 映射组装结果，禁止逐行合同调用造成 N+1。

投影不是授权或交易事实。账号存在性与状态校验、认证、锁定、邀请关系、会员授予、钱包调账、下单、购买和任何资金或权益决定必须调用实时 Reader 合同，不得读取 `commerce_reader_search_projection` 作决定。投影查询失败按管理端依赖故障返回，不降级为跨域 SQL；一致性检查发现漂移时记录指标并阻止将受影响结果误称为权威账号状态。

## 9. 错误处理

每个 `contract` 包定义稳定错误分类，不泄漏基础设施：

- Reader：账号不存在、禁用、认证失效、邀请关系不存在；
- Commerce：商品不可用、报价变化、余额不足、幂等冲突、支付状态冲突；
- Novel：书籍/章节不存在、未发布、对象不可用、对象完整性异常；
- Platform：事务失败、依赖暂不可用和超时。

Provider 把 `sql.ErrNoRows`、约束错误和基础设施错误转换为合同错误。错误保留 `errors.Is` 或等价分类能力，但不携带表名、SQL、对象键、DSN 或凭据。

Reader 兼容层是唯一 Reader HTTP 错误映射位置，保持冻结 HTTP 状态、业务 code/message、data 空值和认证语义。管理端继续使用 `apperror` 与 GVA 适配器，不能复用 Reader 包装。

未知错误返回安全通用文案，并在 HTTP 或任务边界按 request/trace ID 记录一次结构化日志。写请求不做隐式自动重试，依靠既有幂等键处理客户端重试。MinIO 对象缺失、大小不符或哈希异常保持独立完整性错误。

事务内任一合同错误触发全部回滚。`AfterCommit` 缓存失效失败不反转已提交事实，只记录指标和脱敏日志，由 TTL 或后续重试收敛。

## 10. 测试策略

### 10.1 静态边界

- 保持 `TestModuleDependencyRules` 原样，不增加白名单；
- 使用 Go AST 扫描业务实现中的 SQL 字符串，并通过领域表注册表验证所有权；
- 禁止业务模块导入其他领域非 `contract` 包；
- 验证 `initialize` 是唯一跨域实现装配位置；
- 为 Provider Adapter 增加编译期合同断言。

SQL 扫描只分析 Go 源码中的字符串常量和组合表达式；动态表名必须由同领域显式白名单构造，不能用无法审计的任意字符串规避检查。

### 10.2 合同与单元测试

- Reader Handler 使用合同替身逐接口验证路由、认证、业务 code/message、空值、日期和 Long ID；
- Reader、Commerce、Novel 合同覆盖正常、未找到、禁用、冲突、暂时故障和未知错误；
- Transactor 覆盖提交、回滚、嵌套加入、panic 回滚和 AfterCommit；
- 批量投影覆盖稳定排序、缺失关联和无 N+1；
- Commerce Reader 搜索投影覆盖字段约束、幂等 upsert、删除、账号写失败回滚及投影写失败导致账号事实回滚；
- 静态测试禁止 Commerce 运行时代码读取 `reader_accounts`，并禁止交易决策依赖搜索投影。

### 10.3 真实 PostgreSQL 集成

- 奖励失败时邀请注册不留下任何部分事实；
- 并发点赞/取消后关系数与 `like_count` 精确一致；
- 购买任一阶段失败时订单、扣款、流水和权益全部回滚，重复请求幂等；
- 模拟充值、支付回调和人工补单并发时首充奖励只有一份；
- 统一锁顺序在并发压力和超时下不产生循环死锁；
- `00059` 在空库和已有 Reader 数据库上正确创建并回填投影，重复迁移不新增或丢失记录；
- 旧账号迁移同步维护投影，检查点恢复和幂等重跑后账号与投影零差异；
- 订单、充值订单按用户名筛选的总数和分页准确，钱包按用户名/昵称筛选且包含无钱包账号；
- 一致性检查能发现缺失、多余和字段漂移，并通过合同修复后归零。

### 10.4 全量回归

- 使用 `CGO_ENABLED=0 GOCACHE=/tmp/moonbook-gocache` 执行相关 Go 单元、集成和 vet；
- 在 Linux 执行 `go test -race`；
- 边界和 SQL 所有权测试全部通过；
- `make verify-m3`、冻结 Reader 树差异、536 个基线用例、SSR、契约和浏览器关键旅程通过；
- 管理端相关 API、页面测试、ESLint 和生产构建通过；
- 路由清单对比证明冻结 Reader 路径、方法和响应合同无变化。

当前管理前端构建包含已确认恶意依赖。实现阶段不得把旧构建产物作为可信证据；若安全整改尚未先完成，管理前端生产构建项必须保持明确 No-Go，不能伪造通过。本模块整改可以先完成不执行该恶意构建的后端与合同验证，最终 M7 仍须在安全整改后执行可信全量构建。

## 11. 实施顺序

1. 建立 Platform Transactor、嵌套事务和 AfterCommit 测试；
2. 建立三个领域 contract 包、错误分类和 Provider Adapter；
3. 新增 `00059` Commerce Reader 搜索投影、已有账号回填、同步合同和一致性检查；
4. 让 Reader 账号写流程和旧账号迁移在同一目标事务维护投影；
5. 把 Reader-facing Commerce Handler 迁入 Reader 兼容层并保持逐接口合同；
6. 把公开内容、账号商业视图和个人内容投影改为批量合同；
7. 重构邀请注册、点赞、购买和首充奖励为上下文事务参与者；
8. 使用 Commerce 自有投影替换管理端 Reader 搜索 JOIN，并通过合同替换商品目标和购买快照跨域 SQL；
9. 增加 SQL 所有权门并清除全部违规；
10. 执行分层与全量回归，更新 M7 后端质量报告和进度文档；
11. 按 Platform、投影、合同/兼容层、各跨域工作流和验收证据拆分简体中文提交。

每一步先补失败测试，再做最小范围实现。不得一次移动所有包后再集中修复，也不得在中间提交弱化冻结 Reader 契约。

## 12. 验收条件

只有以下条件全部满足，模块边界整改才能关闭：

1. 15 处跨模块实现引用全部消除，`TestModuleDependencyRules` 原样通过；
2. Reader、Commerce、Novel 不直接访问其他领域拥有的表，SQL 所有权测试通过；
3. Reader 拥有全部冻结 Reader HTTP 路由、认证、DTO 和错误映射；
4. `initialize` 是唯一实现装配位置，业务包只依赖合同；
5. 注册奖励、点赞、购买和首充奖励具备原子回滚、幂等和并发证据；
6. 跨域查询使用批量合同且无 N+1；Commerce 管理搜索投影保持准确筛选、总数、分页和无钱包账号语义；
7. 冻结 Reader 契约、Long ID 字符串、SSR 和关键旅程无回归；
8. Go 普通测试、vet、Linux race 和真实 PostgreSQL 集成通过；
9. M7 后端质量报告固定到验收 commit，工作区干净且修改按功能提交；
10. `00059` 回填、账号事务同步、旧迁移同步及一致性检查证明 Reader 账号与 Commerce 搜索投影零差异，交易决策不依赖投影；
11. 受恶意依赖阻断的管理构建仍明确记录为 M7 安全 No-Go，直到独立安全整改完成并重新验收。

本整改关闭模块边界与后端质量阻断，不单独宣称 M4-M7 或生产切换就绪完成。
