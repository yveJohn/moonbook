# Moonbook 支付地址自动生成与 GM Pay v2 同步设计

## 1. 文档状态

- 日期：2026-08-28
- 状态：设计已获用户批准
- 范围：支付渠道配置表单、管理 API、PostgreSQL 配置模型和 GM Pay v2 订单状态同步
- 影响服务：`server`、管理前端 `web`

## 2. 背景与目标

当前支付渠道要求管理员分别填写创建订单、回调、跳转、健康检查和订单同步五个完整地址。五个地址实际只来自 EPUSDT 和读者端两个基础地址，人工维护容易出现路径、协议或环境前缀不一致。

生产支付服务为 GM Pay（原 EPUSDT）v2.0.0。其创建订单接口为 `POST /payments/gmpay/v1/order/create-transaction`，公开订单状态接口为 `GET /pay/check-status/{trade_id}`。Moonbook 现有同步客户端仍使用固定地址发送带签名的 `POST JSON`，与 GM Pay v2 不兼容。

本次目标是：

1. 管理员只填写 EPUSDT 基础地址和读者端基础地址；
2. 五个业务地址全部由后端按固定规则生成，不能人工覆盖；
3. PostgreSQL 只把两个基础地址作为地址配置事实来源；
4. 订单同步适配 GM Pay v2，同时禁止使用无签名状态响应直接完成财务入账。

## 3. 方案选择

采用“后端保存两个基础地址并在读取和运行时派生端点”的方案。

未采用以下方案：

- 同时保存基础地址和五个派生地址：存在重复事实，路径规则变更后可能产生不一致；
- 仅由管理前端拼接地址：其他 API 调用者仍能提交任意端点，后端运行配置无法保证一致性。

后端是地址生成和校验的唯一权威。前端只负责收集两个基础地址和展示后端规则对应的只读预览。

## 4. 地址模型与生成规则

支付渠道新增以下配置字段：

- `epusdt_base_url`：EPUSDT/GM Pay 基础地址；
- `reader_base_url`：读者端公网基础地址。

两个值都必须是绝对 HTTP/HTTPS origin，只允许协议、主机和可选端口。禁止用户信息、非根路径、查询参数、锚点和 opaque URL。保存前去除末尾斜杠，数据库保存规范化结果。

后端按以下固定规则生成地址：

| 用途 | 生成规则 |
| --- | --- |
| 创建订单 | `{epusdt_base_url}/payments/gmpay/v1/order/create-transaction` |
| 回调 | `{reader_base_url}/prod-api/reader/payment/epusdt/notify` |
| 跳转 | `{reader_base_url}/me/recharge` |
| 健康检查 | `{epusdt_base_url}/` |
| 订单同步模板 | `{epusdt_base_url}/pay/check-status/{trade_id}` |

`trade_id` 必须作为单个 URL path segment 进行转义后替换，禁止直接字符串拼接未转义的网关订单号。

已有渠道若没有两个基础地址，保持“配置未完成”状态，由管理员重新填写。系统不从历史派生地址反向猜测基础地址，也不自动启用渠道。

## 5. 管理 API 与页面

支付渠道新增和修改请求使用 `epusdtBaseUrl`、`readerBaseUrl`，不再接受五个派生地址作为写入字段。即使调用者额外提交旧字段，后端也不得将其作为运行配置来源。

查询响应返回：

- 两个规范化基础地址；
- 五个由当前规则生成的完整地址；
- 现有的凭据配置状态、启用状态和超时配置。

管理表单的“接口地址”区域只提供两个可编辑输入框。五个生成地址以只读形式展示，并为每项提供复制图标。保存载荷只包含两个基础地址，不包含预览结果。

渠道完整性判断改为：PID、Secret、EPUSDT 基础地址和读者端基础地址均已配置。渠道未完整配置时不得启用。

## 6. GM Pay v2 订单同步

同步操作读取本地订单的 `gateway_trade_id`，请求：

```text
GET {epusdt_base_url}/pay/check-status/{escaped_trade_id}
Accept: application/json
```

客户端沿用渠道请求总超时，限制响应体大小，并要求 HTTP 2xx。响应必须符合 GM Pay envelope，且 `data.trade_id` 与本地 `gateway_trade_id` 完全一致。

状态处理规则：

| GM Pay 状态 | Moonbook 处理 |
| --- | --- |
| `1` 等待支付 | 保持本地等待支付状态，记录同步结果 |
| `2` 支付成功 | 本地已支付时幂等返回；本地未支付时标记 `callback_exception` 并记录“网关已支付但缺少有效回调”，不直接入账 |
| `3` 已过期 | 将允许同步的未支付订单更新为已过期，并释放活动订单限制 |
| `4` 等待选择网络/币种 | 记录网关状态，保持未支付，不完成入账 |

GM Pay v2 公开查单响应只有 `trade_id` 和 `status`，没有回调签名、金额、收款地址和区块交易哈希。因此它不能满足 Moonbook 财务入账证据要求。只有现有的 GM Pay HMAC-SHA256 签名回调可以将订单更新为已支付并写入钱包流水。

同步发现状态 `2` 与本地状态不一致时，管理端提示管理员在 GM Pay 后台对该订单执行“重发回调”。本次不保存 GM Pay 管理员账号或 JWT，也不自动调用高权限管理接口。

## 7. 一致性、审计与错误处理

- 同步更新订单状态和写入同步审计记录必须处于同一 PostgreSQL 事务；
- 已支付订单同步必须幂等，不能重复写钱包流水或邀请奖励；
- 网络错误、超时、非 2xx、超大响应、非法 JSON、未知状态和 `trade_id` 不匹配均视为同步失败；
- 同步失败不得覆盖已支付状态，不得释放仍无法确认的活动订单；
- 日志和管理响应不得包含 PID、Secret、完整签名或应用主密钥；
- 健康检查仍只执行短超时 GET，并仅把 HTTP 2xx 视为可达；
- 基础地址允许内网地址和显式端口，以支持同机 Docker 部署，但只能由具备支付渠道管理权限的管理员修改，并记录操作审计。

## 8. 数据库迁移

通过新的递增 PostgreSQL 版本迁移为支付渠道表增加两个基础地址字段。不得修改已经执行的 `00073_payment_channel_secure_crud.sql`。

既有五个地址列暂时保留以避免破坏已执行迁移和回滚路径，但不再作为新运行配置的事实来源。新代码不得同时写入两套地址配置。后续只有在单独批准的数据清理设计中才能移除旧列。

迁移不得启用现有渠道，不得猜测或回填生产域名，不得修改支付凭据和历史订单。

## 9. 测试与验收

后端测试至少覆盖：

- 两个基础地址的规范化和五个地址的确定性生成；
- 非 HTTP/HTTPS、用户信息、路径、查询参数和锚点拒绝；
- 创建、修改、查询和启用完整性判断只依赖两个基础地址；
- GM Pay 状态 `1`、`2`、`3`、`4` 的映射；
- 状态 `2` 不直接入账，签名回调仍可完成后续入账；
- `trade_id` 转义、响应订单不匹配、未知状态、超时和超大响应；
- 同步审计、事务回滚和已支付幂等行为；
- Long ID 继续以 JSON 字符串输出和提交。

管理前端测试至少覆盖：

- 表单只允许编辑两个基础地址；
- 五个生成地址只读展示且可以复制；
- 新增、编辑和启停请求不提交旧的五个地址字段；
- 无效基础地址阻止保存；
- 编辑已有未配置渠道时不反推历史地址。

验证包括 Go 相关单元与集成测试、管理前端测试和生产构建。数据库变更必须在项目专用真实 PostgreSQL 容器从空库及现有迁移版本验证，确认迁移历史正确且关键业务数据不减少。

## 10. 发布影响

发布顺序为数据库迁移、`server`、管理前端 `web`。发布后需要重启 `server` 和 `web`，读者前端 `reader-ui` 与网关配置不需要因本次代码变更重启。

发布后现有支付渠道保持停用和未配置状态。管理员重新填写两个基础地址及必要凭据、保存并执行连通性检查后，才能手动启用渠道。真实支付验收必须另行明确授权，不在本设计的自动验证范围内。
