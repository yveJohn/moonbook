# Moonbook 用户反馈 Server酱通知设计

## 1. 背景与目标

读者已经可以通过 `POST /reader/me/feedbacks` 提交反馈，管理后台也已经具备反馈列表、详情和回复能力。本次改动在反馈成功写入 PostgreSQL 后，立即通过 Server酱向管理员发送通知，缩短新反馈的发现时间。

本次只增加自动通知，不增加测试通知按钮，不修改冻结版 `reader-ui`，也不改变现有反馈接口的请求、响应或错误契约。

## 2. 已确认决策

- 触发时机：新反馈成功落库后立即发送。
- 发送方式：在当前反馈请求内同步调用 Server酱，调用完成或超时后再返回现有成功响应。
- 失败语义：Server酱配置缺失、超时、网络失败或返回失败均不回滚反馈，也不向读者返回失败，避免用户重试产生重复反馈。
- 配置入口：管理员通过 Gin-Vue-Admin 现有“参数管理”维护，不增加独立配置页面。
- 交互范围：不提供测试通知入口，只在真实新反馈产生时发送。
- 密钥安全：SendKey 使用项目统一的 `MOONBOOK_APP_MASTER_KEY` 和 `internal/platform/secretcrypto` 加密后存入 PostgreSQL，不新增主密钥。

## 3. 参数约定与管理行为

保留以下两个系统参数键：

| 参数键 | 参数名称 | 存储方式 | 取值 |
| --- | --- | --- | --- |
| `serverchan.enabled` | Server酱反馈通知开关 | 明文 | `true` 或 `false` |
| `serverchan.send_key` | Server酱 SendKey | AES-GCM 密文 | 管理员输入的有效 SendKey |

`serverchan.enabled` 缺失、为空、格式非法或不为 `true` 时均按关闭处理。开关启用但 SendKey 缺失、为空、无法解密或格式非法时跳过发送并记录脱敏错误。

参数管理服务对 `serverchan.send_key` 实施专用保护：

- 新建或更新时，对管理员提交的明文加密后再写入 `sys_params.value`；
- 加密作用域固定为表 `sys_params`、记录 `serverchan.send_key`、字段 `value`，避免依赖数据库自增 ID；
- 列表、详情以及按键查询接口不得返回密文或明文，统一返回掩码 `********`；
- 更新时提交掩码表示保留原值，提交新的非空值才重新加密；
- 禁止把其他参数改名为保留键，或把保留键改为其他键，以免绕过加密及掩码规则；
- 同一保留键只允许存在一条记录，创建重复键时返回明确的参数错误；
- 删除 SendKey 后通知自然变为不可用，不保留可恢复的明文副本。

系统不在迁移文件中写入 SendKey。管理员需在参数管理中创建上述参数；建议先保存 SendKey，再将开关设为 `true`。配置变更按请求实时读取，无需重启后端。

## 4. 组件边界

新增独立的平台通知组件，避免读者域直接依赖 Server酱协议细节：

1. `FeedbackNotifier`：读者反馈服务依赖的窄接口，只接收反馈 ID、读者 ID、提交时间和内容。
2. Server酱配置仓储：从 `sys_params` 读取开关和加密 SendKey，并通过统一加密服务解密。
3. Server酱 HTTP 客户端：负责请求构造、超时、响应状态及业务响应校验，不访问数据库。
4. 参数敏感值保护：位于现有系统参数服务边界，仅针对保留键执行加密、掩码、保留原值和改名限制。

读者 `me.Service` 只在仓储成功返回新反馈后调用 `FeedbackNotifier`。Notifier 为空时采用无操作实现，以保持单元测试、契约测试和其他装配场景稳定。

## 5. 数据流

```text
Reader POST /reader/me/feedbacks
  -> 校验并规范化反馈内容
  -> INSERT reader_feedback（成功提交）
  -> FeedbackNotifier.Notify
       -> 读取 serverchan.enabled
       -> 读取并解密 serverchan.send_key
       -> POST https://sctapi.ftqq.com/{sendKey}.send
       -> 校验 HTTP 状态和 Server酱业务响应
  -> 返回原有反馈成功响应
```

通知请求使用独立的 3 秒总超时，并与已经完成的数据库写入解耦。即使客户端在落库后断开，也允许通知在该短超时内完成。首期不做自动重试；一次调用即为有限尝试，可避免不具备幂等键的 Server酱接口产生重复通知。

## 6. 通知内容

- 标题固定为 `Moonbook 新用户反馈`。
- 正文使用 Markdown，包含反馈 ID、用户 ID、提交时间和反馈内容。
- ID 通过十进制字符串格式化，不经过 JavaScript Number。
- 反馈内容保留换行，最多发送前 1,000 个 Unicode 字符；超出时追加明确的截断提示。
- 反馈内容只进入发往 Server酱的请求，不写入通知日志、错误日志或测试快照。
- SendKey 只出现在 HTTPS 请求路径的内存值中，不进入日志、错误文本或指标标签。

## 7. HTTP 与错误处理

客户端使用表单编码向 Server酱发送 `title` 和 `desp`。只接受 HTTPS 固定域名 `sctapi.ftqq.com`，不允许参数管理覆盖目标 URL，避免将 SendKey 和反馈内容发送到非预期地址。

以下情况均视为通知失败但不影响反馈提交：

- 配置关闭、缺失或非法；
- 主密钥不可用、密文损坏或解密失败；
- DNS、连接、TLS、写入、读取或总超时错误；
- 非 2xx HTTP 状态；
- Server酱响应无法解析或业务码表示失败。

结构化日志只记录反馈 ID、用户 ID、失败阶段、HTTP 状态或归一化错误类别，不记录 SendKey、请求 URL、响应原文或反馈全文。配置关闭属于正常跳过，不以错误级别记录；配置不完整和外部调用失败使用警告级别。

## 8. 测试与验证

自动化测试至少覆盖：

- 参数服务对 SendKey 的创建加密、列表/详情/按键查询掩码、掩码更新保留、明文更新重新加密、改名限制和重复键限制；
- 配置仓储对关闭、缺失、非法布尔值、正确解密、错误主密钥和损坏密文的处理；
- HTTP 客户端的目标路径、表单字段、成功响应、非 2xx、业务失败、非法响应和超时；
- 通知正文 ID 字符串、时间、换行保留和 1,000 字符截断；
- 反馈落库成功后调用一次通知器；反馈写入失败时不调用；通知失败时仍返回已创建反馈；
- 现有读者反馈 HTTP 契约响应保持不变；
- 日志和错误断言不包含 SendKey 或完整反馈正文。

验证执行与风险相称的 Go 格式化、相关包单元测试、读者反馈契约测试、参数管理测试及后端构建。若本地集成基础设施可用，再执行 PostgreSQL 集成测试验证真实 `sys_params` 与 `reader_feedback` 数据流。

## 9. 服务影响与部署

本改动影响 Go 后端服务，不影响管理前端和 `reader-ui` 构建产物。部署后需要重启 Go 后端以加载通知组件代码；参数的新建和更新实时生效，之后修改参数无需重启。

运行环境必须已有有效的 `MOONBOOK_APP_MASTER_KEY`，并允许 Go 后端通过 HTTPS 访问 `sctapi.ftqq.com:443`。没有主密钥时仍可提交反馈，但不能保存或读取有效 SendKey，也不会发送通知。

## 10. 明确不做

- 不新增管理页面或测试通知按钮；
- 不修改冻结版 `reader-ui`；
- 不增加通知历史表、Outbox、Worker 或人工重发入口；
- 不自动重试 Server酱请求；
- 不通过环境变量直接配置 SendKey；
- 不把通知失败暴露给读者或回滚已提交反馈。
