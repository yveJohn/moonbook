# 读者购买余额判断修复设计

## 1. 背景

新 Go 后端的章节和整书购买把 `commerce_products.allow_bonus_coin` 传入钱包扣款逻辑。普通按字数计费章节没有独立商品记录，因此该值默认为 `false`，即使金币与钻石合计余额足够，也会因为钻石余额不足返回“余额不足”。整书商品配置错误时也会出现相同行为。

旧 Java 后端对章节和整书统一使用混合扣款：先扣金币，再用钻石补足。既有货币系统设计也规定小说商品允许使用金币。会员购买则始终只使用钻石。

商品迁移的冲突更新当前只同步名称、价格、销售状态和更新时间，没有同步 `allow_bonus_coin` 等配置，重复迁移无法纠正目标库中的错误抵扣配置。

## 2. 目标

- 章节购买始终先扣金币，不足部分扣钻石。
- 整书购买始终先扣金币，不足部分扣钻石。
- 会员购买继续只扣钻石，不使用金币。
- 金币与钻石合计不足时，购买事务完整回滚，不遗留订单、权益或流水。
- 商品迁移重复执行时完整同步影响商品行为的字段。

## 3. 实现方案

### 3.1 购买扣款

购买仓储保留一个混合扣款函数，固定按以下顺序计算：

1. 锁定读者钱包。
2. 金币扣款额取 `min(金币余额, 商品价格)`。
3. 钻石扣款额为 `商品价格 - 金币扣款额`。
4. 钻石余额不足时返回余额不足错误。
5. 在同一事务内分别写入金币和钻石流水。

章节和整书购买直接调用混合扣款，不再读取或依赖商品的 `allow_bonus_coin`。会员购买继续调用仅钻石扣款路径。`allow_bonus_coin` 字段继续保留在商品管理和迁移模型中，以兼容现有数据及其他商品类型，但不改变小说购买的固定业务规则。

### 3.2 商品迁移

`reader_product` 迁移发生主键冲突时，除现有字段外同步：

- `product_type`
- `target_id`
- `allow_bonus_coin`
- `duration_days`
- `sort_order`
- `source_type`
- `source_ref`

迁移仍使用现有幂等写入方式，不新增数据库迁移文件，不修改已执行的 PostgreSQL 结构迁移。

## 4. 错误与事务语义

- 合计余额不足继续映射为读者兼容响应 `code=500`、`msg=余额不足`。
- 报价变化、商品不可用、重复购买和并发购买语义保持不变。
- 任一扣款、流水或权益写入失败时，订单和所有财务写入随事务回滚。
- Long ID 和金额继续以字符串形式输出给读者端。

## 5. 测试

购买集成测试增加以下场景：

- 普通按字数计费章节仅金币余额足够时购买成功。
- 固定价章节即使商品配置禁止金币，仍按小说规则混合扣款。
- 整书即使商品配置禁止金币，仍按小说规则混合扣款。
- 金币与钻石合计刚好等于价格时购买成功。
- 合计余额不足时订单、权益、流水和余额均不变化。
- 会员钻石不足但金币足够时仍返回余额不足。

迁移测试增加重复迁移场景，验证目标商品的金币抵扣、有效期、排序及来源字段被源数据纠正。

## 6. 影响范围

- 影响服务：Go 后端 Reader/Commerce 购买接口、旧数据迁移命令。
- 不修改 `reader-ui` 和管理前端。
- 部署后需要重启 Go 后端；仅执行迁移工具时无需重启前端服务。
