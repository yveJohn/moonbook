# Moonbook 人工补单活动锁修复设计

## 1. 文档状态

- 日期：2026-08-28
- 状态：设计已获用户确认
- 范围：人工补单终态更新、充值建单活动锁自愈、回归测试与生产发布
- 影响服务：`server`

## 2. 已确认问题

生产订单 `RC2089645633658621956` 通过人工补单进入 `paid`，钱包流水和
`manual_success` 审计均已写入，但订单仍保留 `active_reader_id`。随后同一读者的
建单请求命中该活动订单；现有仓储只允许活动订单处于 `creating`、
`gateway_unknown` 或 `pending`，遇到 `paid` 时返回未分类错误，Reader 因而显示
`internal service error`，且不会创建新订单。

正常 GM Pay 回调结算会清除 `active_reader_id`，缺陷仅存在于人工补单更新语句。
当前生产遗留行也需要在不直接修改生产数据的前提下恢复。

## 3. 方案选择

采用“双层防护”方案：

1. 人工补单在写入 `paid`、钱包流水和审计的同一事务中将
   `active_reader_id` 置空，保证以后不再产生终态活动锁；
2. 建单取得读者 advisory lock 后，如发现活动订单已是终态，则在同一事务中幂等
   清除该遗留锁并继续建单。

未采用以下方案：

- 只修改生产数据：只能解除当前读者阻塞，下一次人工补单仍会复现；
- 只修人工补单：能阻止新增坏数据，但当前生产遗留订单仍会阻止第二次充值；
- 新增数据库迁移批量清理：本次只有运行时状态机缺陷，不需要结构变更或全表数据
  修改，建单事务可在精确读者锁范围内完成安全自愈。

## 4. 状态机边界

建单发现 `active_reader_id` 对应订单时按以下规则处理：

- `creating`、`gateway_unknown`：继续返回现有订单，禁止重复调用 GM Pay；
- `pending`：维持现有行为，将旧订单标记为 `superseded` 并释放锁，再创建新订单；
- `paid`、`create_failed`、`expired`、`superseded`：视为历史遗留终态锁，只清除
  `active_reader_id`，不改变订单状态、支付事实、钱包流水、失败诊断或审计，然后创建
  新订单；
- 其他未知状态：继续拒绝并返回错误，不静默扩大状态机。

自愈更新必须带订单 ID、读者 ID 和终态条件，避免并发或未来状态变化时清除有效锁。
整个读取、清理和新订单写入继续受现有读者 advisory lock 与 PostgreSQL 事务保护。

## 5. 测试与验证

自动化测试至少覆盖：

- 人工补单成功后订单为 `paid`、钱包只入账一次且 `active_reader_id` 为空；
- 人工补单幂等重放不会恢复活动锁或重复入账；
- 建单遇到遗留 `paid` 活动锁时保留旧支付事实并成功创建新订单；
- `pending` 替换和 `creating`、`gateway_unknown` 保护行为不变；
- 相关 Commerce 测试、`go vet` 和真实 PostgreSQL 集成测试通过。

生产发布继续使用 `scripts/deploy-production.sh`。发布后验证新镜像、迁移状态、容器
健康、公网 HTTPS 和错误日志，并由用户创建新的未支付订单确认二维码；不得对已支付
订单重复付款。

## 6. 数据与服务影响

- 不新增或修改 PostgreSQL 迁移；
- 不直接更新生产订单、钱包、回调或审计数据；
- 不修改 `reader-ui`、管理前端、GM Pay、Redis 或对象存储；
- 代码只影响 `server`，但现有生产发布脚本会按固定发布单元重建 `server`、`web`、
  `reader-ui` 和 `gateway`。
