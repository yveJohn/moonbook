## 2. 已确认范围

### 2.1 重构范围

完整迁移旧项目当前管理后台的有效业务能力，包括：

- Gin-Vue-Admin 系统基座、管理员认证、角色、菜单、权限、配置和审计；
- 小说分类、作者、书籍、章节、上下架、标签和相关内容管理；
- 采集、TXT 导入、书籍合并、AI 配置、清洗、摘要、重试及任务管理；
- 读者账号、书架、阅读历史、偏好、点赞、反馈和运营管理；
- 钱包、不可变流水、会员、权益、订单、充值、支付回调和运营统计；
- 封面、章节正文、导入文件、导出文件和其他有效业务附件。

管理页面不复刻旧界面。功能和关键业务闭环必须完整，页面、菜单、组件和交互统一按 Gin-Vue-Admin 体系重做，以业务结果等价而非像素或旧操作路径作为验收标准。

### 2.2 不迁移内容

- 旧管理系统的管理员、角色、菜单、权限及框架配置不转换，使用新 Gin-Vue-Admin 模型重新初始化；
- Redis 缓存、临时文件、纯运行日志和无追溯价值的中间数据不迁移；
- 已废弃或未启用的第三方集成不重新实现；
- 当前 `reader-ui` 未实际调用的历史读者接口不纳入兼容范围。

### 2.3 旧项目与读者端冻结

重构开始后旧项目停止常规开发，只允许生产运行和必要的紧急修复。新功能直接进入新系统。影响读者兼容、数据正确性或安全的紧急修复必须登记并同步到新系统。

现有 `reader-ui` 原样复制进新仓库，保留构建、SSR、测试和静态资源。它在正式切换并通过兼容验收前冻结，原则上不修改业务代码；若存在影响上线的严重缺陷，修复必须同步更新契约基线。

## 3. 总体架构

首期采用单个可部署的 Go 模块化单体：

```text
Gin-Vue-Admin 管理前端 ─┐
                       ├─> Go 模块化单体 ─> PostgreSQL
冻结版 reader-ui ──────┘                 ├─> Redis
                                         └─> MinIO
```

Go 应用按以下业务模块隔离：

1. GVA 基座：管理员认证、RBAC、菜单、系统配置和审计；
2. 小说域：分类、作者、书籍、章节、发布和内容元数据；
3. 读者域与兼容层：账号、认证、书架、阅读、偏好和读者接口 DTO；
4. 内容生产：采集、导入、合并、AI、清洗、摘要和任务；
5. 运营与交易：钱包、流水、会员、权益、订单、充值和支付；
6. 平台能力：文件、对象存储、通知、配置、任务调度和审计。

模块之间通过明确的应用服务接口协作，禁止跨模块直接操作其他模块的内部表或对象。管理 API 与读者兼容 API 使用独立路由组、DTO、鉴权入口和响应封装，Gin-Vue-Admin 的管理端响应格式不得泄漏到读者接口。

采集、AI、导入和迁移等长任务首期由单体内独立 Worker 池执行，任务状态持久化。模块边界应允许未来将 Worker 独立部署，但首期不引入微服务、服务发现或分布式事务。

## 4. 数据与存储设计

### 4.1 PostgreSQL

PostgreSQL 保存结构化业务事实、关系、状态和对象引用。新表按业务域重新设计，不要求兼容旧 MySQL 表结构。

全部旧业务 ID 原值迁移为 PostgreSQL `bigint`，包括书籍、章节、读者、作者、订单、流水和任务等。新 ID 生成规则必须以迁移后最大值为边界并避免冲突。Go 与数据库内部可以使用整数，但所有面向 JavaScript 的 ID 字段必须序列化为 JSON 字符串，管理前端也只能按字符串处理和提交。

财务领域以不可变钱包流水、订单和权益记录作为事实来源。余额等汇总数据必须能由事实记录核对，不允许迁移过程中静默调整差额。

### 4.2 MinIO

所有非结构化内容进入 MinIO，包括：

- 章节正文；
- 书籍封面；
- TXT 等导入原文件；
- 导出文件；
- 业务附件及其他有效文件。

PostgreSQL 仅保存对象键、版本、SHA-256、字节数、内容类型、状态和业务关联。读者端不直接访问章节正文的 MinIO URL，必须通过兼容 API 获取正文。

章节正文采用 UTF-8 纯文本和每章独立的版本化对象，默认对象键约定为：

```text
chapters/{bookId}/{chapterId}/v{version}.txt
```

对象键是内部实现细节，不进入读者接口契约。封面和其他文件使用各自的命名空间，并保留哈希、大小和来源信息。

### 4.3 跨存储一致性

章节创建或更新采用以下流程：

1. 校验正文并计算哈希；
2. 上传新的版本化 MinIO 对象；
3. 在 PostgreSQL 事务中写入或切换对象引用；
4. 数据库提交后失效 Redis 缓存；
5. 延迟回收无引用的旧对象和失败上传产生的孤立对象。

该顺序保证 PostgreSQL 不会指向尚未上传成功的对象。上传成功但数据库提交失败时，新对象暂时成为孤立对象，由可审计的回收任务清理。章节和文件删除默认采用业务软删除与延迟对象清理，避免立即造成不可恢复的数据损失。

### 4.4 Redis

Redis 只承担缓存、限流、短期会话和任务协调，不保存唯一业务事实。所有 Key 必须带模块及版本前缀，配置明确 TTL，并能够从 PostgreSQL 与 MinIO 重建。涉及余额、订单、权益或迁移进度的最终事实不得只存在 Redis。

## 5. 读者 API 零修改兼容

### 5.1 契约来源

兼容范围以冻结版 `reader-ui` 的真实调用面为准。实施第一阶段同时扫描：

- `reader-ui` API 调用、类型定义、鉴权封装和 SSR 请求；
- `reader-ui` 单元、集成及页面测试；
- 旧 Java 后端对应控制器、DTO、异常和业务实现。

由此生成可审阅、可执行的接口清单。旧 Java 后端用于补全实际语义，但不会将当前读者端没有调用的历史接口自动纳入范围。

### 5.2 兼容维度

每个接口必须保持：

- 路由前缀、路径、HTTP 方法和 Content-Type；
- 查询参数、路径参数、请求体和 Header；
- HTTP 状态码、业务 `code`、`message` 和 `data` 包装；
- 缺省值、`null`、空数组、分页结构和日期格式；
- ID 字符串形态及超过 JavaScript 安全整数的边界值；
- Token Header、登录响应、未登录、过期、封禁和权限不足语义；
- 浏览器及 SSR 调用所需的 CORS、Cookie 和缓存行为。

兼容层使用专用 DTO 和适配器，内部领域模型变化不得直接改变读者响应。

### 5.3 鉴权切换

正式切换后旧 Token 全部失效，新后端返回现有 `reader-ui` 可以识别的未登录语义，用户需重新登录。旧密码摘要原值迁移并兼容旧算法验证；首次成功登录后可以渐进升级到新密码算法。

新会话继续使用冻结版前端预期的 Token 传递方式。日志不得记录密码、完整 Token、支付凭据或其他秘密。

### 5.4 章节读取

Go 服务先校验章节状态和读者权益，再根据 PostgreSQL 对象引用读取 MinIO。热点正文可以使用 Redis 或进程缓存，但返回结构和业务行为必须与旧接口一致。

对象缺失、哈希异常和 MinIO 超时必须记录结构化错误与追踪 ID，对外转换为冻结版 `reader-ui` 能处理的既有错误结构，不泄漏对象键、内部存储地址或基础设施错误。

## 6. 第三方集成

只迁移当前实际启用且仍有业务价值的支付、AI 模型、邮件、采集代理及其他外部服务。每项集成必须具备：

- 显式启用开关；
- 环境变量或 Secret 注入的凭据；
- 合理的连接、读取和总超时；
- 有上限的重试与退避；
- 幂等或去重策略；
- 结构化失败记录与管理端重试入口；
- 敏感信息脱敏。

生产密钥和旧仓库中的历史凭据不得复制进新仓库。

## 7. 数据迁移

### 7.1 数据源与范围

正式迁移时，旧系统停止写入，迁移程序直接连接只读 MySQL。迁移前必须生成可恢复备份，当前已知备份约为 8 GB。备份用于恢复和审计，不替代正式迁移程序的只读数据源。

迁移全部有效业务数据，包括小说、章节、读者、密码摘要、书架、历史、余额、流水、会员、权益、订单、支付记录、评论反馈、作者、采集与 AI 任务、封面和附件。业务结果和需要追溯的任务记录迁移；缓存、临时中间数据和纯运行日志不迁移。

### 7.2 迁移程序

迁移工具按主键范围或游标分批读取，禁止一次将全部数据载入内存。它必须支持：

- 阶段和批次检查点；
- 中断恢复；
- 幂等重跑；
- 可配置批量大小和并发；
- 显式转换错误清单；
- 源 ID 原值保留；
- 正文及文件的大小与 SHA-256 校验；
- 结构化进度和耗时统计；
- 不包含秘密及完整敏感正文的日志。

迁移前先执行容量盘点，统计各表行数和容量、主键范围、章节正文总字节数、预计对象数、附件容量、孤立关联和异常数据。实际批量大小及并发以盘点和生产数据副本演练结果确定。

### 7.3 强制校验

迁移报告至少包含：

- 逐表源/目标行数、主键范围、空值和枚举分布；
- 书籍、章节、正文、作者和分类的关联完整性；
- 读者、书架、历史、点赞、反馈和偏好的关联完整性；
- 钱包余额与流水汇总、订单金额、支付记录和权益的一致性；
- MinIO 对象数量、总字节、缺失对象和哈希结果；
- 所有转换错误及人工处置结论；
- 冻结版 `reader-ui` 契约测试与关键用户旅程结果。

财务核对必须零差异。不可解释的行数差异、对象缺失或静默丢弃均阻止上线。

## 8. 正式切换与回退

允许的停机窗口为 12 小时以内。正式切换前至少完成一次使用生产数据副本的全量演练，并为正式窗口保留安全余量。演练不能稳定落入窗口时，必须先优化迁移工具。

切换顺序如下：

1. 确认备份成功并可读取；
2. 停止旧系统写入；
3. 执行源数据预检和容量核对；
4. 分批迁移结构化数据；
5. 上传并校验章节正文和其他 MinIO 对象；
6. 执行全量自动核对；
7. 执行管理端、读者契约及关键业务冒烟；
8. 由负责人依据 Go/No-Go 报告确认切流；
9. 切换 Go 后端、管理前端和原样迁入的 `reader-ui`；
10. 进入受控观察期。

Go 条件：迁移程序没有未处理错误，财务零差异，关键实体及对象完整，契约与核心业务旅程通过，并且剩余时间满足预设安全余量。

No-Go 条件：任一财务差异、对象缺失、不可解释的行数差异、读者契约失败、核心业务失败或已经超过预设的最晚回退时间点。

切流前旧系统和 MySQL 保持未修改状态，可直接恢复旧入口。正式方案必须在演练后确定“最晚可回退时间点”。切流后若需回退，必须先停止新系统写入并评估观察期产生的新数据；禁止新旧系统无控制地同时写入。

## 9. 部署与运维

首期使用单机 Docker Compose 部署 Go 应用、PostgreSQL、Redis、MinIO 和反向代理。设计同时满足后续迁移到 k3s：

- Go 服务保持无状态；
- 配置使用环境变量，秘密使用 Secret；
- PostgreSQL、Redis 和 MinIO 使用独立持久卷；
- 不依赖宿主机固定业务路径；
- 提供独立的存活和就绪检查；
- 支持优雅停机和任务租约释放；
- 镜像、配置和数据生命周期分离。

运行基线包括结构化日志、请求及任务追踪 ID、接口延迟和错误率、Worker 队列与失败数、PostgreSQL 连接、Redis 命中率、MinIO 请求错误与容量指标。关键异常必须告警。

PostgreSQL 与 MinIO 需要协调备份策略，并定期执行恢复演练。仅证明备份文件存在不算恢复能力得到验证。

## 10. 任务可靠性与安全

长任务必须使用持久化状态机、租约或锁、幂等键、有上限重试、指数退避和人工重跑入口。应用重启后可以恢复未完成任务，不能依赖进程内队列作为唯一状态。

安全基线包括管理员 RBAC、关键操作审计、登录限流、最小权限数据库及对象存储凭据、支付回调验签、防重放、敏感字段脱敏和依赖漏洞检查。管理员权限与读者身份体系相互隔离。

## 11. 测试策略

测试分层如下：

1. Go 单元测试、Vue 组件测试和迁移转换测试；
2. 使用真实 PostgreSQL、Redis 和 MinIO 的集成测试，不使用 SQLite 或本地文件替代生产组件；
3. 管理 API、第三方适配器和读者兼容契约测试；
4. 冻结版 `reader-ui` 的现有测试、SSR 请求和关键页面旅程；
5. 管理端关键业务端到端测试；
6. 迁移全量演练、性能测试、安全检查及备份恢复演练。

每个业务域只有在后端、管理页面、数据映射、迁移规则和自动化测试同时完成后才视为完成。

- 正式切换在 12 小时内完成，或在最晚回退时间点前安全执行 No-Go。

## 14. 明确延后事项

- k3s 清单和集群高可用部署延后到 Compose 版本稳定后；
- 微服务拆分延后，除非实际容量或独立扩缩容需求证明必要；
- 未被冻结版 `reader-ui` 调用的历史读者接口不实现；
- 已废弃或未启用的第三方集成不实现；
- 读者端新功能在正式切换验收后再恢复开发。
