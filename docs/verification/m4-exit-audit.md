# M4 交易、支付与运营退出审计

审计日期：2026-08-15

## 结论

M4 当前未满足退出条件。钱包、不可变流水、签到、邀请、会员、消费购买、模拟充值、人工补单、充值订单查询、主动同步和当前旧表迁移已有直接证据；Reader 发起真实 EPUSDT 充值、完整回调审计、充值失败状态机和财务全域核对仍存在实现或验证缺口。

本审计只记录当前代码事实，不把真实支付环境验收替代为本地实现，也不把订单查询和主动同步视为支付创建闭环。

## 已证明能力

- 钱包余额由不可变流水维护，人工调账具备请求幂等、事务锁和余额不足保护。
- 签到奖励重复请求只产生一条奖励流水；邀请注册奖励和首充奖励具备业务幂等键。
- 书籍购买并发测试证明八个并发请求只产生一个订单、两条扣款流水和一个权益事实。
- 会员人工发放按请求 ID 幂等，限时和永久发放可独立叠加。
- 模拟充值采用创建 `pending` 订单和单独确认入账两阶段流程；人工补单、模拟充值和 EPUSDT 成功入账共用首充奖励幂等事实。
- 管理端可查询充值订单与回调日志，并可执行受控主动同步和人工补单。
- `reader-finance` 在隔离 MySQL 8.4 和 PostgreSQL 17 上验证当前财务表迁移、幂等重跑、旧 ID 保留、秘密脱敏和钱包流水零差异。

## 支付创建缺口

冻结 Reader 在创建充值订单后立即依赖支付地址和以下状态：

`creating`、`pending`、`gateway_unknown`、`create_failed`、`superseded`、`expired`、`callback_exception`、`paid`。

当前 `commerce/recharge.SQLRepository.CreateOrder` 直接写入本地 `pending` 订单，未调用 EPUSDT 创建交易接口，也不会填充 `gateway_trade_id`、`actual_amount`、`receive_address` 或 `payment_url`。因此数据库虽允许全部状态，运行路径只证明了本地 `pending` 创建和后续成功入账，不能证明真实 Reader 充值可用。

旧实现还包含以下当前未实现的行为：

- 先持久化 `creating`，再在事务外调用网关；
- 校验网关订单号、金额、币种、Token、状态和过期时间；
- 区分确定失败的 `create_failed` 与结果不确定的 `gateway_unknown`；
- 同一请求 ID 返回原订单且不重复调用网关；
- 新活动订单将同一读者的旧活动订单转为 `superseded`；
- 到期订单进入 `expired`，Reader 停止轮询。

该缺口需要先完成已启动的支付创建设计确认，再按设计实现本地 HTTP 替身和真实 PostgreSQL 集成测试。不得使用真实生产支付凭据或执行真实支付。

## 回调审计缺口

当前成功回调在钱包入账、首充奖励、订单 `paid` 转换和成功日志之间保持同一 PostgreSQL 事务，重复成功回调不会重复入账。但是 HTTP 处理器在以下场景会在写日志前返回：

- 请求体为空、过大或 JSON/字段格式非法；
- PID 不匹配或签名非法；
- 订单不存在、金额/Token/状态不匹配；
- 链上交易哈希被其他订单占用；
- 已支付订单收到不同交易哈希。

重复成功回调同样只返回成功，不新增一次回调尝试记录。因此当前管理端回调日志不是“每次尝试”的完整审计轨迹，尚不能证明拒绝原因、防重放和异常处理可追溯。

## 测试覆盖缺口

现有测试直接证明了成功回调重复入账幂等、购买并发唯一性、模拟充值幂等、人工补单保护和首充奖励跨入口幂等。仍缺少以下退出证据：

- EPUSDT 创建成功、明确拒绝、超时、非法响应和订单字段不匹配；
- 同请求并发创建只调用一次网关；
- 新订单替换旧活动订单以及过期状态转换；
- 无效签名、格式错误、金额不匹配和交易哈希重放均写入脱敏回调日志；
- 多个并发有效回调只产生一条充值流水、一条首充奖励和一个订单终态；
- 失败、退款或失效后的订单、会员和权益状态转换及核对结果。

## 财务核对范围

`commerce/reconcile.Wallets` 当前逐读者、逐币种核对钱包余额、累计收入和累计支出，迁移集成测试另对合成夹具执行指定订单、签到、邀请、充值和回调行断言。这证明钱包核对器及当前夹具映射有效，但不是订单、支付、权益的通用全域核对器。

M4 退出前需要提供可执行核对，至少覆盖：

- 每个已支付充值订单恰好关联一条充值流水，金额和读者一致；
- 链上交易哈希、请求 ID 和首充奖励业务键全局唯一；
- 每个已支付消费订单的扣款拆分等于订单价格；
- 每个成功购买或发放与相应会员/权益事实一致；
- 退款、失败、关闭、失效状态不会保留不应存在的有效权益；
- 回调成功事实、订单终态和钱包入账不存在孤立记录。

完整约 8 GB 副本的行数、主键、金额分布和耗时报告仍归 M6；M4 必须先完成核对器本身及合成边界数据验证。

## 管理能力矩阵缺口

旧管理 API 还定义了 `GET /reader/checkin/list` 和 `GET /reader/inviteReward/list`。冻结旧钱包页面未调用这两个函数，但它们是有效的只读运营审计能力。用户已选择将其补为可见审计页签；在设计流程完成前不修改页面和路由。

## Compose 配置缺口

`.env.example` 声明了 EPUSDT PID、Secret 和主动同步 URL，但根 `compose.yaml` 的服务环境锚点没有注入这些变量，健康检查 URL也未出现在模板中。即使宿主机配置了变量，Go Server 容器也无法读取当前支付验证和同步配置。支付创建设计还需补充创建接口、公开回调 URL和 Reader 跳转 URL，并通过配置合同、Compose 模型和无秘密扫描验证。

## M4 退出门

只有同时满足以下条件，才能把 M4 标记为完成：

1. 完成真实网关创建适配器的本地替身实现与全部失败状态测试；
2. 每次回调尝试均有脱敏、可关联、可检索的审计记录；
3. 成功、失败、重复、重放和并发状态机测试通过；
4. 签到和邀请奖励记录审计页签通过桌面与移动端 E2E；
5. 订单、支付、钱包、奖励、会员和权益通用核对器零差异；
6. EPUSDT 变量完整注入 Compose，仓库不包含真实凭据；
7. 使用受控真实支付环境完成的连通性和沙箱验收作为切换前外部证据，不替代上述本地完成项。
