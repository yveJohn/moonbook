# 生产回退 Runbook

回退只在 Go/No-Go 负责人批准后执行。本项目不自动执行生产回退，也不连接生产资源。

## 触发条件

- 迁移核对出现不可解释差异；
- Reader/管理核心旅程或正文对象持续失败；
- 钱包、订单、支付或权益状态出现非幂等异常；
- 错误率、延迟、数据库或 MinIO 健康指标超过批准阈值；
- 在最晚回退时间前无法完成验证。

## 步骤

1. 记录触发时间、版本、请求 ID/trace ID、指标快照和当前迁移 checkpoint；停止新系统入口写入，保留审计日志。
2. 导出新系统切换期间新增的订单、钱包流水、会员/作品权益、Reader 账号变化和任务状态，计算 SHA-256 并由数据负责人保管。
3. 保持新系统 PostgreSQL/MinIO 只读，禁止删除、覆盖或 `TRUNCATE` 任何数据。
4. 恢复旧系统入口和反向代理；确认旧系统健康、只读/写入策略和支付回调路由符合批准方案。
5. 对切换期间新增事实制定单独的数据处置方案：能安全重放的进入人工审核队列，不能重放的保留差异清单；禁止未经批准直接双写或反向修改旧表。
6. 重新执行旧系统登录、书库、章节、钱包/订单只读核对和支付回调替身冒烟。
7. 形成回退报告，包含触发原因、时间线、数据差异、备份/恢复证据、未决风险和下一次 Go/No-Go 修复项。

## 回退完成标准

- 旧系统入口健康且错误率恢复到批准阈值；
- 新系统切换期间事实已完整封存并完成差异登记；
- PostgreSQL、MinIO 和备份未被破坏性操作改变；
- 用户批准后才允许重新规划迁移或再次切换。
